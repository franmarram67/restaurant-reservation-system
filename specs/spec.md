# Spec of Restaurant Reservation System

Restaurant Owners can create many Restaurants. Restaurants have 1 Grid (1:1). In the Grid there will be displayed Tables with a top left starting point and a bottom right end point, each a point in the Grid. Each Table will have a max capacity, a set integer. Each Restaurant will have a Schedule with Opening and Closing Hours per day of the week, when they're closed and when they're open. As well as being able to set specific holidays each year that they will not be open. Also Restaurants can choose intervals where people can book, so for example each 1 hour, each 30 minutes, each 15 minutes, each 5 minutes and so on. Restaurants can also choose duration of each Reservation, for example 1h. Restaurants will have a buffer time set for x amount of minutes, e.g. 15minutes. If there is a reservation and a buffer time there won't be any slots available until the buffer time is completed, and even then the next available slot won't necessarily be available right at the time the buffer time ends, depending on the Restaurant's configuration. For example: Restaurant has 1h reservation duration and a booking interval of 30 minutes, so there will be slots available for 18:00, 18:30, 19:00 and 19:30. Let's say there is a booking for 18:00 that lasts 1h plus 15 minutes buffer time. The next available slot won't be 19:15 but 19:30 as the buffer time will simply block the 19:00 slot. If for example the booking interval is 15 minutes, then the one for 19:15 will be available. This keeps our logic simpler and more straightforward. When setting up the tables, they will be shown in the Grid and displayed to the Restaurant Owner to see, the grid could be totally filled in with tables, but it is usual that there will be spaces for waiters and customers to walk through. The Grid is just a basic representation of the table / seating area layout in a rectangular fashion subdivided by squares (points in the grid). There might be some JS in the Grid representation to the Restaurant Owner as they decide to fill in the Grid with Tables, they will select in the Grid the spaces for the Table. The end customer can create Reservations, based on the configuration of the Restaurant (so duration, start time). The user will input the amount of people to book a reservation. The system then will prioritize fitting all the people in one table of matching size 1:1, so for example 6 people reservation, the system will return all available 6 person tables to the customer and won't return available all the other tables as it is trying to fill them in just one Table. If for example the Restaurant only had a maximum of 4 person tables but also had 2 person tables, for the same 6 person booking, the system will display both 4 person tables and 2 person tables, and then the customer should pick tables until the maximum capacity is reached, in this case 1 4 person table and 1 2 person table. It would be for the availability, the customer and the restaurant in-site to decide if the Tables could be joined together or not, but the system won't be able to guarantee that. There will be JS for the customer to pick the corresponding tables. If for example there wouldn't be any 2 person tables available, then the system will try to pick the right kind of capacity per table to not leave any Table with empty seats. In this case if there are 3 person Tables, the system will display all 3 person Tables and let the customer pick 2. Let's say there isn't a combination that perfectly matches the Reservation number of people, in this case the system will try to leave as little amount of empty seats as possible. So let's say there would be a booking of 5 people, and there are only 4 person and 2 person Tables available. The system will try to return 4 person and 2 person table to the user. For only 4 person tables and a 6 people reservation, then the system will return only 4 person tables and allow the user to pick two. What the system wants is to avoid people not to book, and try it's best to meet the total capacity with no empty seats. All this logic will need to be coded in the backend. The users won't need to be registered in the app to book. The customer will need to put their full name, phone number and email, and after the reservation is created will receive and email with the data. If the customer doesn't turn up on time, the staff of the Restaurant could make the slot available for new customers to come in. This will be a manual process. The email sent to the customer will contain a link to edit the reservation as well as to cancel it. The Reservation will be able to have one of the following statuses: pending, confirmed, seated, completed, cancelled, no_show. Each reservation will have a number of people, and will provide the customer data as described previously only for the Customer that made the reservation. When a Customer creates a Reservation, they don't have to pay (at least this will be our initial configuration). If another Customer is trying to book the same table, but the first Customer books, the backend will return an error saying that the Table has been booked and to please select another one, effectively returning available tables as previously stated or alternatively returning no available Tables. This will prevent multiple people booking the same table accidentally. Restaurants will have an optional maximum party size for Reservations. A Restaurant can have Staff Accounts associated with it. For each Restaurant, the Restaurant Owner / Admin and Staff accounts will be able to see the Dashboard for that Restaurant. The Dashboard will contain a timeline of the reservations per day, time and table. Through this Dashboard, the proper accounts will be able to change the Reservation statuses to no_show if people don't turn up, as well as create new Reservations for people that just walked in. After a Reservation is made, there will be an email sent (as previously said). If the Customer cancels the Reservation, another email will be sent. There will be a reminder email the day before the Reservation and 1h before the Reservation. These emails can be in Laravel queues.
